## 0. 목적 — 이 2주가 증명해야 하는 것

Phase 0은 기능 개발이 아니라 **데이터 스택 역전(게이트 G2)의 실측 검증**이다. BOL(미국 세관 수입기록) 기반 발굴이 Apollo 키워드 기반보다 실제로 우월한지, 숫자 3개로 판정한다:

| # | 측정 지표 | 정의 | 제안 임계값 (Go 기준) |
|---|---|---|---|
| M1 | **노이즈 비율 (2축)** | ①포워더·3PL·통관사 비율 + ②대기업·OEM 직수입 비율 (각각 별도 집계) = 노이즈 건수 ÷ 전체 consignee | 합산 < 50% (필터 후 < 10%) |
| M2 | **이메일 적중률** | 벤더 조회 20개사 중 유효(verified) 이메일 확보 회사 수 ÷ 20 | ≥ 60% |
| M3 | **검증 바이어 1건당 비용** | (벤더 API 비용 + 유료 툴 비용) ÷ 유효 이메일 확보 건수 | ≤ 3,000원/건 |
| M4(보조) | 실수입 증거 커버리지 | 최종 후보 중 최근 12개월 내 해당 HS 수입기록 보유 비율 | 기록용 (콜드메일 첫 줄 카피 근거) |

- 임계값은 제안값 — **스프린트 종료 시 Jay가 실측치를 보고 Go/No-Go 판정**한다.
- Go → Phase 1(데이터 엔진) 착수 + G2 정식 채택 + 1부 XML v1.1 개정(No.2 소스 열 BOL 중심으로 정정).
- No-Go → Apollo 벌크 대안 재검토 (단, ToS 리스크 P0는 여전히 유효하므로 사실상 파라미터 조정 후 재시도가 우선).

## 2. 산출물 (Deliverables)

리포 내 `engine/` 디렉토리 신설 (프론트 데모와 분리):

```
engine/
├── phase0/
│   ├── raw/bol_extract_[HS]_[date].csv     # W1 — ImportYeti 수동 추출 원본
│   ├── scripts/
│   │   ├── clean_bol.py                    # 정제 스크립트 (정규화 + 포워더 필터)
│   │   ├── forwarder_keywords.txt          # 포워더 판별 키워드 리스트 (누적 관리)
│   │   └── enrich_contacts.py              # W2 — 벤더 건별 조회 (rate limit + 캐시)
│   ├── out/
│   │   ├── companies_normalized.csv        # 정규화 회사 테이블
│   │   ├── companies_top20.csv             # 조회 대상 20개사
│   │   └── contacts_cache.json             # 조회 결과 캐시 (보존기한 90일 필드 포함)
│   └── REPORT.md                           # M1~M4 실측 리포트 + Go/No-Go 판정 자료
```

**정규화 회사 테이블 스키마** (`companies_normalized.csv`):

| 필드 | 설명 |
|---|---|
| company_id | 내부 ID |
| name_raw / name_normalized | 원본 표기 전체(중복 병합 이력) / 정규화 회사명 |
| entity_type | buyer / forwarder / oem_large / unknown (2축 노이즈 필터 판정 결과) |
| hs_codes | 수입 HS코드 목록 |
| shipment_count_12m / last_shipment_date | 최근 12개월 선적 횟수 / 최종 선적일 |
| origin_countries | 수입 원산지 (한국·경쟁국 표시) |
| state / city | 소재지 (P2 국가 라우팅 대비 — 미국 내 주 단위) |
| confidence | 정규화 신뢰도 (low는 검수 큐 대상) |

## 4. 하드 제약 (위반 금지)

1. **발송 없음** — 이메일 1통도 보내지 않는다. 발송은 Phase 2(도메인 워밍업 완료 후).
2. **벌크 금지** — 세관 데이터 크롤러 자동화 금지(수동 추출), 벤더 벌크 CSV 다운로드 금지 (ToS 리스크 P0).
3. **최소 수집** — 회사 단위 정보 우선. 담당자 개인정보는 Top 20 조회분만, 캐시에 보존기한 명기 (privacy_timing_model ①수집 최소화).
4. **재배포 금지** — 산출 CSV·캐시는 리포 내 보관하되 외부 공유 금지. `engine/phase0/raw/`와 `out/`, 캐시는 `.gitignore` 처리(연락처 포함 파일은 커밋 금지 — 스크립트와 리포트만 커밋).
5. **용어** — 산출물·리포트에서 D3 용어 체계 준수 (BOL 모니터링 → 내부 문서 한정, 고객 대면 표현 금지 항목 사용 금지).

## 5. 알려진 함정 (handoff §pitfall)

- **회사명 정제가 최대 난관** — "ABC Corp" / "A.B.C. Corporation" / "ABC CO.,LTD" 병합. fuzzy 매칭만으로 부족하면 LLM 배치 판별(비용: 수백 건 기준 $1 미만). 병합 이력을 name_raw에 보존해 오병합 롤백 가능하게.
- **포워더 consignee 가림** — consignee가 포워더 명의면 실바이어가 안 보임. 이 비율 자체가 M1의 일부이므로 "가려진 비율"도 별도 집계 (BOL 한계 정량화 = D2 집행 스택 한계 문서화에 재사용).
- ImportYeti 무료 티어의 조회 제한 — 걸리면 추출 기간을 12→6개월로 축소, 표본 축소를 리포트에 명기 (F8 최소 표본 원칙 준수).

## 6. Phase 0의 비종속성 & 다음 연결

- **게이트 G1(성사비 형태)과 무관** — Phase 0은 수익 모델을 건드리지 않으므로 즉시 착수 가능.
- **게이트 G2는 Phase 0이 곧 검증 수단** — 별도 결정 대기 없이 착수하고, REPORT.md가 G2 판정 자료가 된다.
- Go 판정 시 Phase 1(데이터 엔진 2~3주)로: 수집 자동화, LLM 배치 정규화+검수 큐, HS·인증 태그 스키마, pgvector 매칭 v1, 멀티 벤더 어댑터 2개.
- **병행 액션 (Phase 0과 동시, handoff 즉시 액션 #6):** 전용 발송 도메인 구매 + 워밍업 개시 — 워밍업 4~6주 캘린더 리드타임 때문에 Phase 2를 기다리면 늦는다. Phase 0 D1에 도메인만 사두고 백그라운드 진행.
