## 항목별 검증

### 1. 수집 데이터 판매 정책 — "판매할 것인지, 메일 발송에서 끝낼 것인지"
**상태: △ 부분 반영 (결정은 존재, 명시 문서 없음)**
- 결정 내용: **데이터 자체는 판매하지 않는다.** 상품은 "검증된 매칭 + 발송 + 트래킹 + 보고서" 번들이며, 이는 "그냥 Apollo에서 데이터 사면 되지 않냐"는 가격 경쟁력 리스크에 대한 대응 논리로 확정됨 (③ §3 리스크 표).
- 구조적 뒷받침: 리스트 브라우징 화면 부재, 연락처 완전 비노출, 회사명 마스킹 (④ 전체 구조 + hard constraints) — 판매할 수 있는 형태로 노출 자체가 안 됨.
- **갭:** "데이터 비판매" 결정이 정책 문서에 한 줄로 명시돼 있지 않음. → **조치: 운영정책 확정안 v1.1에 P-00 "데이터 비판매 원칙" 항목 추가 권고** (아래 후속 액션 #1).

### 2. 데이터 정제 — "난잡한 키워드를 어떻게 분류·매칭할 것인지" (가장 중요)
**상태: ✅ 반영**
- 방향 확정: 키워드 카테고리 분류는 불가능·비효율로 판정 (라이브 데모에서 CNC 업체가 'ISP', 'Government'로 라벨링된 사례 확인) → **키워드 분류 대신 AI 유사도 매칭** (③ §2-1).
- 정제 파이프라인 정의: 입수 시 ① 이메일 verify ② AI 한 줄 요약 생성(배치) ③ 키워드 임베딩 생성 ④ BRONZE 부여 (② §6).
- raw 키워드는 유저에게 노출하지 않고 AI 한 줄 요약으로 대체 (④ 추천 카드 구현).

### 3. 매칭 방식 — "서술형+AI vs 박스형 카테고리"
**상태: ✅ 반영 (서술형 우선 확정)**
- 8/13 회의에서 개발팀 스스로 서술형 우선으로 결론 ("카테고리로 다 나누는 건 불가능... 입력도 주관식으로"), 토큰 비용 우려는 "그렇게 많이 안 든다"로 해소 (③ §2-1).
- 산업 대분류는 **최후의 보루**로 보조 유지 + 기타 직접입력 병행 (① 화면 3).
- 데모 구현: 서술형 textarea 주력 + 대분류 select 보조 + 인증 체크박스 (④ ProfileSetup). 파생 아이디어인 "가입 시 유사 바이어 5개 미리보기"까지 구현 (④ PreviewHook).

### 4. 데이터 노출 제한 — "요금제별 노출 정책"
**상태: ✅ 반영**
- 요금제별 월 자동 추천: Free 3 / Standard 10 / Premium 20, **Premium은 수량이 아닌 품질(GOLD 우선) 차등** (⑤ P-10).
- 노출 수준: 회사명 부분 마스킹, 이메일·연락처 완전 비노출, AI 한 줄 요약 + 국가/주·분야·규모·매칭 근거만 (① 화면 6, ④ 구현).
- 우회 방지: 제외 반복을 통한 사실상 브라우징 차단 — 보충 추천 월 2건 한도 (⑤ P-11).

### 5. 바이어 상위권 진입 로직 — "읽음만으로 상위권이면 무관 카테고리 스팸 발송 불상사"
**상태: ✅ 반영 (지적한 불상사를 명시적으로 차단)**
- 단순 읽음/안읽음 구조가 아님: engagement score = 회신 +10 / 첨부 열람 +5 / 열람 +1 / 오프-플랫폼 체크 +15 / 무반응 −2 / 반송 −10 (② §3, ⑤ §3, ④ 스토어 함수로 실사용).
- **핵심 방어: "카테고리 연관성 필터가 score보다 선행"** — 유사도 미달 바이어는 점수 무관 추천 제외 (⑤ §3). 개발팀이 우려한 "읽음 수집용 무관 카테고리 발송 유인"을 정확히 차단하는 조항.
- 위양성 방어: SILVER 진입은 열람 2회+ or 첨부 1회 (⑤ P-08).

### 6. 이메일 트래킹 — "도메인별 편차, 리소스 삽입 방법 권장"
**상태: ✅ 반영 (권장안 그대로 채택)**
- 리소스(자사 호스팅 이미지+식별 토큰) 삽입 방식 채택, 첨부 아닌 본문 삽입, 수신자 액션 불필요 (③ §1-3).
- 발송은 플랫폼 내부 발송으로 한정 (외부 메일앱이면 트래킹 불가) — 데모도 mailto 없이 내부 발송 UI만 (④).
- 한계 인지 반영: 스팸 필터 강제 로드 위양성 → 열람 인정 기준 5초/2회 가설 + **실발송 테스트 후 확정** 절차화 (⑤ P-09).

### 7. 내부 보고서 자동화 — "'일정 기간' 논의 / 재매칭 여부 / 보고서에 의미 있는 내용"
**상태: ✅ 반영 (3개 하위 질문 모두 답변됨)**
- "일정 기간" → 확정: 팔로업 D+7, 매칭 해제 D+14(2회 발송 기준) (⑤ P-01·P-02).
- "재매칭 필요 여부" → 확정: 해제 시 바이어는 등급 재산정 후 풀 복귀 + 유저 슬롯은 신규 추천 충전, 동일 유저 재추천 금지 6개월 (⑤ P-01·P-12, ① 화면 8, ④ 해제 임박 뱃지 구현).
- "단순 읽음/안읽음으로는 보고서에 의미 없다" → 보고서 구성을 확장: 월간 funnel(추천/발송/열람/회신) + 바이어별 등급·상태 표 + 날짜 + **오프-플랫폼 활동 체크 5종 + 자유 서술 메모** (개발팀이 예상한 "피드백 각자 입력 + 자유 서술 기능" 그대로) + 거래 단계(미팅→샘플→견적→계약) 연동 (① 화면 9·10, ④ Report+ReplyInbox 구현).
- 보고서의 이중 목적(리텐션 장치 + 오프-플랫폼 활동 회수)도 문서화 (③ §1-5).

### 8. 관리자 페이지 — "무엇을 수집하고 싶은지, 어떤 데이터로 MVP를 고도화할 것인지"
**상태: ✅ 반영 (요건 정의 완료 — 화면 구현은 계획대로 다음 버전)**
- 수집·모니터링 지표 5종 + 경보 기준 정의: 등급별 재고 / 카테고리별 회신율 / 제외 사유 로그 / DEAD 전환율 / 발송률 (⑤ §4, ② §6).
- 고도화 기획: 제외 사유 → 추천 알고리즘 개선 입력값, DEAD 전환율 → 데이터 벤더 교체 판단, 카테고리별 회신율 → 데이터 확장 우선순위 (⑤ 각 항목 근거).
- 데모에서 수집 동작 구현: 제외 사유 선택 모달 → 스토어 기록, COLD/DEAD가 관리자 관점 데이터로 스토어에 존재 (④).
- 관리자 화면 자체는 MVP 범위 밖으로 상호 합의된 상태 (마이그레이션 스펙 out_of_scope) — "없으면 고려 안 하고 개발"이 아니라 **요건은 위와 같이 확정됨**을 회신할 것.

## 결론

디원솔루션이 요청한 정책 8건은 **전부 답변 가능한 상태**다. 7건은 문서·데모에 이미 반영되어 근거까지 추적 가능하고, 1건(데이터 판매 정책)은 결정은 서 있으나 명문화만 남았다. 특히 개발팀이 "가장 중요"(2번)·"중요"(5번)로 표시한 두 항목 — 데이터 정제 방식과 상위권 진입 로직의 스팸 유인 차단 — 은 각각 AI 유사도 파이프라인과 "카테고리 필터 선행" 조항으로 정면 대응되어 있다.
